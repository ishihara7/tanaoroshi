# 要件定義書（案）：備品所在管理システム（NFCタグ × Azure）

作成日：2026-11-16 / 改訂：2026-11-16（運用方針の訂正を反映） / 状態：ドラフト
元資料：`HANDOFF_備品所在管理システム.md`（以下「申し送り」）。**申し送りと本書が食い違う場合は本書を優先する。**

## 1. 目的とスコープ

### 1.1 目的
備品にNFCタグまたはQRコードを貼り、iPhoneでタッチ（読み取り）するだけで所在を記録する。読み取り時にGPSの位置情報を取得してDBに保存し、レーダー画面で、備品がある方向と距離を確認できるようにする。

### 1.2 PoC条件
| 項目 | 内容 |
|---|---|
| 対象 | 3フロア（うち2フロアは別の建物）。**フロア図は使わない** |
| 利用者 | 2名（管理者1名＋利用者。管理者がユーザーを1人ずつ登録） |
| 備品点数 | 最大20個 |
| 端末 | **iPhone（iOS）のみ**。Androidは使わない |
| 期間・成功基準 | 未定。暫定基準は「主要機能が動作すること」 |
| ネットワーク | 制限なし（インターネット公開、ログインで保護） |
| 可用性・保持期間 | 特に要件なし |

### 1.3 スコープ外
- **場所タグ**（場所タグ → 備品タグの2段階タッチは行わない）
- **Android専用画面**（連続スキャン、タグ書き込み画面）
- 持ち出し／返却、貸出状態、返却期限・通知
- 備品の状態管理（廃棄のみ「台帳から非表示」で扱う）
- ユーザーの一括登録、専用の訂正・取消機能

## 1.4 削除した機能（2026-11-16）
運用に不要と判断し、次の機能を削除した（コード・画面・DB定義から外した）。
- **フロア図**：画像のアップロード、位置合わせ、図上のピン表示、「建物外の可能性」の判定。画像の保存先（Azure Blob Storage）も不要になった。
- **備品の種別**：種別の管理画面、備品への種別の設定、検索・CSVの種別の列。区別が必要なときは、名称・備考に書く。
- 種別の列が付いた古いCSVは、取り込める（使わない列として、結果に表示する）。

## 2. 確定した方針・仕様

| 項目 | 決定内容 |
|---|---|
| タッチ（読み取り）するもの | 備品のタグ（NFCタグまたはQRコード）のみ |
| 位置の記録 | タグの読み取り直後に、**最大8秒**位置を取り続け（誤差10m以下で終了）、**一番精度のよい1件**をDBに保存。拒否・時間切れのときは、位置なしで記録（最後の位置は上書きしない） |
| マップ（削除） | **フロア図は使わない**（2026-11-16に機能を削除）。位置は、GPSの緯度・経度と誤差で保持し、レーダー画面で方向と距離を示す |
| 所在の粒度 | **GPSだけで記録し、エリア単位で割り切る**（2026-11-16の実測：誤差15〜17m）。部屋・棚は特定しない。場所タグは使わない。画面には、「おおよその位置」の注記と誤差を表示する |
| 所在の見せ方 | **レーダー画面**：探したい備品を選ぶと、スマホの現在地と、備品が最後に記録された位置から、方向と距離を示す。スマホの向きはiPhoneのコンパス（初回に「モーションと方向」の許可）。誤差が距離より大きいときは、方向は当てにならない旨を画面に表示する |
| 棚卸の判定 | 場所単位の「他の場所の物」判定は行わない。棚卸は、備品タグを読み取って位置と最終確認日時を更新し、一定期間（90日）未確認の物を一覧する |
| GPS誤差の扱い | 誤差が大きくても記録し、画面に誤差を表示する |
| 位置情報の許可 | 初回に案内ページを表示し、サイトの位置情報を「許可」にするよう利用者へ案内（iPhoneの設定で「毎回確認」を「許可」へ） |
| 棚卸 | 棚卸のときも備品タグを読み取り、位置の更新と所在確認（最終確認日時の更新）を行う |
| タグ書き込み | NFCタグは、iPhoneの市販アプリ（NFC Tools等）で、1枚ずつ手動で書き込む。QRコードは、管理画面からラベルを印刷する（システムによる書き込み支援・UIDのひも付けはしない） |
| 管理番号 | 既存の資産番号。**半角英数字のみ、1〜20文字**（申し送りの「10桁の数字」から変更）。**大文字・小文字は区別しない**（`ab12`と`AB12`は同じ備品。表示は入力どおり）。常に文字列で扱う（先頭の0を保つ）。出典は他の管理表／システム |
| 備品の種別（削除） | **種別は使わない**（2026-11-16に機能を削除）。区別が必要なときは、名称・備考に書く |
| iPhoneでの記録 | タッチしたら自動で確定。誤記録は正しい位置で再タッチして更新（履歴は残る） |
| 廃棄 | 管理者が「廃棄」操作で台帳から非表示（履歴は残る） |
| 権限 | 一般／管理者の2段階 |
| ログイン状態 | Cookieは30日（設定で変更可）。Secure・HttpOnly・SameSite=Lax。端末紛失時は管理者がユーザーを無効化 |
| パスワード | 12文字以上、argon2でハッシュ化。初期パスワードでログイン後に本人が変更。忘れた場合は管理者が初期化（メール送信なし） |
| ログイン試行制限 | 5回失敗で15分ロック（自動解除） |
| QRコード（追加） | NFCタグと同じURLを、QRコードのラベルとして印刷できる（QR＋管理番号、本体20〜50mm、裁断用の点線）。QRの誤り訂正はM。NFCタグと併用できる。URLの長さの制限（NTAG210）は、QRには無い。**運用方針：社内で使う備品はQR、社外に持ち出す可能性のある備品はNFCタグ**（システム上の区分は設けない。運用のルールとして扱う） |
| タグURL | `https://{ドメイン}/i/{暗号化した識別子}`。**URLに管理番号を載せず、備品ごとに発行するランダムな短いトークン（12文字程度、推測不能）に置き換える**。DBで管理番号と対応づける（鍵管理は不要）。PoCはNTAG215（504バイト）前提のため、現在の長いホスト名（約77バイト）のまま運用する。NTAG210（48バイト）は使わない。本番化でカスタムドメインに切替える際は、タグを書き直す（そのためPoC中はタグをロックしない） |
| 備品の項目 | 管理番号・名称・備考のみ（種別・メーカー・型番・シリアル・写真は扱わない。必要なら備考に記入） |
| 移動履歴 | 備品ごとに日時・記録者・誤差を一覧表示（最新50件）。すべて保存し削除しない |
| ドメイン | 仮ドメイン（azurewebsites.net）。タグはロックしない |

技術スタック、Azure構成は申し送り3・6章のとおり。

## 3. 運用フロー

### 3.1 導入（管理者）
1. 管理者アカウント作成 → ユーザーを1人ずつ登録
2. 備品を登録（管理番号・名称）。CSV取込も可
3. 備品にタグを付ける：QRラベルを印刷して貼る（社内の備品）、または市販アプリでNFCタグにURLを書き込んで貼る（社外に持ち出す可能性のある備品）

### 3.2 日常の所在記録（iPhone）
1. 備品タグにタッチ → 通知をタップ → URLが開く（未ログインなら、ログイン後に元URLへ戻る）
2. 位置を最大8秒調べ、一番精度のよい1件を自動で記録（再読み込みでは記録しない）
3. 画面に備品名・記録した位置の誤差を表示。「今の場所で記録し直す」ボタンもある

### 3.3 棚卸
1. 対象の備品タグを順にタッチ → 位置を更新し、最終確認日時を更新
2. 一定期間（初期90日）確認されていない備品を一覧で確認

### 3.4 確認・管理
- レーダー：備品を選ぶと、現在地からの方向と距離を表示
- 備品検索：管理番号・名称。詳細に、移動履歴
- 管理者：備品・ユーザーの管理、QRラベルの印刷、廃棄操作、パスワード初期化

## 5. データモデルの変更点（申し送り5章に対して）
- `locations`、`inventory_sessions`、`inventory_results` は廃止
- `assets`：`current_location_id`／`home_location_id` を、最新の緯度・経度・誤差に置き換える。`status`、`holder_name`、`due_date`、`tag_uid`、`tag_type`、種別、フロアは持たない。廃棄は `is_active`
- `scans`：`scan_type` は持たない（タッチの記録のみ）。緯度・経度・誤差・高度・エラーは保存（追記のみ）
- `assets`：URL用の `tag_token`（ランダム12文字程度、一意）を追加。トークンは管理者が備品登録時に発行し、書き込み用に表示する。再発行も可（古いタグは無効になる）

## 6. 非機能要件・注意点
- 小規模PoC（2名・20点）のため、性能要件は設けない
- GPSは屋内で10〜数十mずれる。位置は「おおよその位置」である旨を画面に明示し、誤差を表示する
- 位置情報の記録は、タグにタッチした直後に、**最大8秒だけ**位置を取り続け（誤差10m以下になれば、そこで終了）、**一番精度のよい1件だけ**をサーバーに送って保存する（2026-11-16に「瞬間の1回」から変更。最初に返る位置が粗いことが多いため）。ページの再読み込み・戻る・タブの復元では、自動では記録しない（ボタンで記録し直せる）。**例外：レーダー画面を開いている間だけ**、スマホの位置を連続で取得するが、**端末内で計算するだけで、サーバーには送らず、保存もしない**（歩いた軌跡は残さない。画面を閉じると取得も止まる）
- レーダーの利用者：ログインした全員。備品は名称・管理番号で検索して選ぶ
- HTTPSのみ、未ログインには備品情報を見せない、秘密情報はリポジトリに含めない
- Azureリソースの作成・変更・課金操作は、実行前にコマンドを提示して承認を得る
- **記録者は、社員番号だけを保存・表示する**（2026-11-16。氏名・アカウント名は、画面とCSVに出さない）。位置を調べている間（最大8秒）に、社員番号を入力する。2回目以降は、端末に記憶して自動入力し、位置が取れ次第、自動で記録する。入力のない記録は、受け付けない（半角英数字、20文字まで）。認証は、ログイン必須のまま（社員番号は、本人確認ではなく、記録者の目安）
- **データの暗号化（2026-11-16に設定を確認）**
  - 通信：ブラウザ〜Web Appは、HTTPSのみ（TLS 1.2以上）。Web App〜Azure SQLも、暗号化した接続（Encrypt、証明書を検証）
  - 保存：Azure SQL の透過的データ暗号化（TDE）が有効（サービス管理キー。バックアップも暗号化）
  - **座標は、列単位の暗号化はしていない**（数値のまま保存）。DBに直接アクセスできる人には、読める。管理者のCSV出力にも含まれる
  - パスワードは、argon2のハッシュで保存。タグのURLは、管理番号を含まないランダムなトークン
  - 自宅など、社外で記録された位置は、個人の居場所に近い情報になるため、取り扱いを、運用ルールで決める（案：本人への周知と同意、保管期間、座標を見られる人の限定）

### 6.1 位置情報の実測結果（2026-11-16、iPhone、`/test/geo`）
- 対象：太田開発センター2F、7か所（南東・武尊・事務エリア・榛名・浅間・倉庫・赤城）×各3回＝21件
- 誤差（自己申告）：14〜17m（中央値17m）。座標の最大の広がり：約19m（東西方向）
- **21件中14件が、場所によらず同一の座標**（36.292588, 139.376258）。屋内ではWi-Fi等による推定位置が返っているとみられる
- 部屋の違いより、同じ部屋内のばらつきの方が大きく、**部屋の区別はできない**
- 高度は全件46mの固定値で、使えない
- PCのブラウザ（Windows）の測位は誤差63mと大きく、iPhoneとは別物（評価から除外）
- 他の2フロアは別の建物のため、今回は未測定（あとで測定する）
