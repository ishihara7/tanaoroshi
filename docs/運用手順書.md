# 運用手順書：備品所在管理システム

## 1. 全体像
備品に貼ったNFCタグにiPhoneをかざすと、その瞬間のGPS位置が記録されます。備品検索から、最後の記録の方向と距離を示す**レーダー**で探せます。

- **位置の精度**：屋内の実測で、誤差は約15〜17mです。「このセンター内のどのあたり」までが目安で、部屋や棚は特定できません（2026-11-16、太田開発センター2Fでの実測）。
- 画面にも、「おおよその位置」「誤差」を表示します。

## 2. 最初のセットアップ（管理者）

### 2.1 最初の管理者を作る
Azure の DB に、このPCから直接つないで作成します（パスワードは、ご自身で入力します）。
```powershell
cd c:\works\tanaoroshi
foreach ($n in "DB_SERVER","DB_NAME","DB_USER","DB_PASSWORD") {
  $v = az webapp config appsettings list -g rg-tanaoroshi -n rs-mobi-tana --query "[?name=='$n'].value | [0]" -o tsv
  Set-Item -Path "Env:$n" -Value $v
}
$env:DB_TRUSTED = "false"
.venv\Scripts\python.exe -m app.cli create-admin <ログインID>
Remove-Item Env:DB_SERVER, Env:DB_NAME, Env:DB_USER, Env:DB_PASSWORD, Env:DB_TRUSTED
```

### 2.2 ユーザーを追加する
管理者でログイン → 上部の「ユーザー」→ ログインID・権限を入力して追加します（**氏名・表示名は、扱いません**。画面上部には、ログインIDが表示されます）。
- **初期パスワードは自動で発行され、その画面に一度だけ表示されます**。本人に安全な方法で伝えてください。
- 本人は、初回ログイン時にパスワードを変更します（12文字以上）。
- パスワードを忘れたときは、「PW初期化」で再発行します。
- 端末を紛失したときは、「無効にする」で、ログインを止めます。
- ログインに5回失敗すると、15分間ロックされます（自動で解除されます）。

### 2.3 備品を登録する
- 1件ずつ：「備品」→ 管理番号（半角英数字、1〜20文字。大文字・小文字は区別しません）・名称を入力して登録します。
- まとめて：「備品」→「CSV取込」。1行目に見出し（`管理番号,名称,備考`）を書いたCSVを選びます。種別などの、使わない列は、無視されます。
  - 文字コードは、UTF-8 か Shift_JIS です。
  - **Excelで、管理番号の先頭の0が消える**ときは、列の書式を「文字列」にしてください。
  - **1件でも誤りがあると、何も登録されません**。表示された行を直して、もう一度取り込みます。
  - 登録済みの管理番号は、飛ばされます（同じファイルを何度取り込んでも安全です）。

## 3. NFCタグの書き込み

### 3.1 書き込むURLの確認
「備品」→ 対象の備品を開く →「NFCタグに書き込むURL」を使います。
```
https://<ホスト名>/i/<ランダムな12文字>
```
- **URLに、管理番号は含まれません**。
- 現在のホスト名は長いため、URLは約77バイトです。**NTAG215（504バイト）なら書き込めます。NTAG210（48バイト）には、書き込めません。**

### 3.2 書き込み（iPhone、市販アプリ）
1. App Store の NFC 書き込みアプリ（例：NFC Tools）を開きます。
2. 「書き込み」→「レコードを追加」→「URL」→ URLを貼り付けます。
3. タグにiPhoneをかざして書き込みます。
4. **書き込み後に、そのタグを読み取って、備品の画面が開くことを確認します**。
5. 備品に貼ります（金属面に貼る場合は、金属対応のタグを使います）。

### 3.1.1 タグ書き込み時のシステム構成
タグ（NFC・QR）に入れる内容は、**システムが発行するURL**です。書き込み自体は、システムの外のアプリで行います。

```
管理者 → [システム（Azure）] ─┬─ URLをコピー → [NFC Tools（iPhone）] → NFCタグ
          備品を登録            │
          ランダムなURLを発行   └─ QRを生成   → [ブラウザで印刷]       → QRラベル
          （DBに保存）
```

| 役割 | 内容 |
|---|---|
| システム（App Service＋SQL Database） | 備品の登録時に、ランダムなURLを自動で発行し、備品と対応づけてDBに保存する。QRコードの生成・ラベルの印刷用ページの表示。**管理番号はURLに含めない** |
| NFC Tools（iPhoneの市販アプリ） | 管理画面でコピーしたURLを、NFCタグに書き込む。**システムとは連携しない**（タグのUIDの記録などもしない） |
| ブラウザ（印刷） | 管理画面の「QRラベルの印刷」から、A4・実寸（100%）で印刷する |

- 書き込んだあと、**そのタグを読み取って、備品の画面が開く**ことを確認します。
- URLを再発行すると、書き込み済みのタグ・ラベルは、使えなくなります（書き直し・貼り替えが必要）。

### 3.2.0 QRとNFCタグの使い分け（運用のルール）
| 備品 | 使うもの | 理由 |
|---|---|---|
| **社内で使う備品** | **QRコード**（ラベルを印刷して貼る） | 書き込み不要で、まとめて作れる。金属面にも貼れる。社内なら、QRが見えても問題ない |
| **社外に持ち出す可能性のある備品** | **NFCタグ** | QRは社外の人にも見え、社内システムのURLが、写真に撮られる。NFCは、触れないと読めず、URLも見えない。ラベルの擦れ・汚れの影響も、受けにくい |

- システム上の区分（フラグ）は、ありません。どちらも**同じURL**なので、どちらで読んでも、同じ記録になります。運用のルールとして、使い分けます。
- 備品に、QRとNFCタグの**両方を貼って**もかまいません。
- **ノートPCなどの金属の備品にNFCタグを貼る**ときは、**金属対応のタグ**を使い、貼った状態で読み取れることを、必ず確認してください。金属対応のタグが NTAG210（48バイト）の場合、現在のURL（約77バイト）は書き込めません（短いカスタムドメインにするか、別のタグにします）。

### 3.2.1 QRコードのラベル（NFCタグの代わり、または併用）
NFCタグと同じURLを、QRコードにして貼ることもできます。読み取ると、NFCタグと同じ画面が開き、同じ記録がされます。

1. 「備品」→「QRラベルの印刷」を開きます。
2. QRの大きさ（本体の1辺。初期値30mm）、切り取り線、名称の有無、印刷する備品を選びます。
3. 「印刷用のページを開く」を押し、開いたページで、ブラウザの印刷を使います。**用紙はA4、倍率は「100%（実際のサイズ）」**にします（拡大・縮小すると、QRの大きさが変わります）。
4. 点線に沿って、切って貼ります。

| 切り取り線 | 内容 |
|---|---|
| 裁断用（既定） | ラベルを隙間なく並べ、行・列を貫く点線。カッターで、まとめて切れます |
| 1枚ずつ囲む | ラベルごとに囲む点線。はさみ向き |
| なし | 線なし |

- ラベルには、QRコードと**管理番号**（名称は、初期は印刷しません。チェックを入れると、印刷できます）が載ります。QRの中身は、管理番号ではなく、NFCタグと同じトークンつきのURLです。
- 大きさの目安：最小20mm（近くで読む場所）、**標準30mm**、50mm（少し離れて読む場所）。QRの周りの白い余白（4マス分）が、必須です。切るときは、この余白を残してください。
- 白地に黒、つや消しのラベルを使います。光沢があると、反射で読めません。屋外・汚れる場所では、耐水のラベルを使います。
- 備品ごとのQRは、備品の編集画面にも表示されます（SVGで保存もできます）。
- 備品に、QRとNFCタグの、両方を貼ることもできます。

### 3.3 ロックについて（重要）
**ドメインが確定するまで、タグをロックしないでください。** ロックは元に戻せません。ホスト名を変えると、書き込み済みのタグは使えなくなります。

### 3.4 タグのURLを作り直す（紛失・流出したとき）
備品の画面で「URLを再発行」します。**以前のタグは、使えなくなります**。新しいURLを、タグに書き込み直します。

## 4. 日常の使い方（利用者）

### 4.1 所在を記録する
**読み取り方は、2通りあります。どちらでも、同じ画面が開き、同じ記録になります。**

| 方法 | 手順 | 備考 |
|---|---|---|
| **標準（アプリ不要）** | iPhoneのNFCの位置（本体の上部背面）をタグにかざす → 画面上部の通知をタップ | iPhone XS／XR以降は、アプリを開かなくても、読み取れる。**手順が少なく、おすすめ**（PoCのiPhoneで、読み取れることを確認済み） |
| **NFC Tools** | アプリを開く →「読み取り」→ タグにかざす → 表示されたURLのレコードをタップして開く | 以前の運用。タグの中身（URL）も確認できる。アプリを開く手間が、1つ増える。標準の方法が使えない古い機種でも使える |

NFC Tools は、**タグへの書き込み**には必要ですが、**読み取りには必須ではありません**（書き込んだタグを、標準の方法で読めるか、一度ためしてください）。

読み取り後の手順は、共通です。
1. タグにかざす（標準）、またはNFC Toolsでレコードをタップすると、Safariが開きます。
2. 初回は、**ログイン**と、**位置情報の許可**が必要です。位置情報は、「許可」にしてください。
3. タッチ直後の数秒（最大8秒）、「位置を調べています…（誤差 約◯m）」と表示されます。**この間に、社員番号を入力します**（半角英数字、20文字まで。氏名は入力しません）。
   - **初回**：社員番号を入力して、位置が取れたら、**「記録する」を押します**（入力の途中で、勝手に記録されることはありません）。
   - **2回目以降**：社員番号は、この端末に記憶され、自動で入力されます。位置が取れ次第、**自動で記録されます**（番号が違うときは、書き換えて「記録する」を押します）。
4. 「所在を記録しました」と表示されれば、完了です。

**社員番号について**：記録した人を、社員番号で残します（移動履歴と、位置履歴のCSVに表示。**氏名やアカウント名は、表示しません**）。社員番号は、本人の確認はしていないため、あくまで「誰が記録したか」の目安です。共通のアカウントでログインしても、社員番号で、記録した人を区別できます。

**再読み込みについて**：ページを再読み込みしたり、閉じていないタブを開き直したりしても、記録は更新されません（その場所で、備品の位置が書き換わるのを防ぐためです）。記録し直すときは、もう一度タグにタッチするか、「今の場所で記録し直す」を押してください。

位置情報が許可されていないときは、位置なしで「確認」だけが記録されます。次を確認してください。
- 設定 → プライバシーとセキュリティ → 位置情報サービス → オン
- 同じ画面の「Safari Webサイト」→「次回確認」または「Webサイトの使用中のみ許可」
- Safari のアドレスバー左の「ぁあ」→「Webサイトの設定」→「位置情報」→「許可」

### 4.2 備品を探す（レーダー）
1. 「検索」で、名称か管理番号を入力して、備品を選びます。
2. 「この備品を探す（レーダー）」をタップします。
3. 「コンパスを使う」を押すと、スマホの向きに合わせて表示されます（初回に許可が必要です）。
4. **距離が誤差の範囲内なら、「近くにいます」と表示され、方向は示されません**。周りを探してください。

レーダーの間だけ、スマホの位置を連続で取得しますが、**この端末の中で計算するだけで、サーバーには送られず、保存もされません**。

### 4.3 要確認リスト
次の備品が表示されます。
- 90日以上、確認（タグへのタッチ）がない備品
- 位置の記録がない備品

### 4.4 棚卸
対象の備品のタグを、順にタッチします。位置と「最後の確認」が更新されます。タッチされなかった備品は、一定期間後に、要確認リストに出ます。

## 6. デプロイ（コードの反映）
1. ローカルでテストを実行します。
   ```powershell
   .venv\Scripts\python.exe -m pytest -q
   ```
2. ZIPを作成します（`requirements.txt` と `app/` だけを含みます。`.env`、`.venv`、`tests` は含めません）。
   ```powershell
   .venv\Scripts\python.exe tools\make_deploy_zip.py
   ```
   出力先は、**`out\deploy.zip`**（プロジェクト内の、Git管理外のフォルダ）です。
3. Azure ポータルで、Web App → 開発ツール → 高度なツール → 移動 → `/ZipDeployUI` に、`out\deploy.zip` をドラッグ＆ドロップします。
4. ビルドと再起動で、約5分かかります。完了後、`/health` が `{"status":"ok"}` を返すことを確認します。

注意：
- **テーブルを変更したとき**（列の追加など）、現在は起動時の自動作成（`create_all`）のため、**既存のテーブルは変更されません**。変更が必要な場合は、先に、データのバックアップとテーブルの再作成を検討します（Alembic の導入は、今後の課題です）。
- SCM基本認証を、デプロイのために一時的にオンにした場合は、**終わったらオフに戻します**。

## 6.5 座標の暗号化と、鍵の管理
備品の位置（緯度・経度）は、**アプリで暗号化して、DBに保存**します（AES-256-GCM）。DBに直接アクセスできる人や、バックアップを入手した人には、座標は読めません。アプリを通した画面と、管理者のCSV出力では、復号して表示します。

| 項目 | 内容 |
|---|---|
| 鍵の置き場所 | 環境変数 `COORD_ENCRYPTION_KEY`（Azure：Web App の「アプリ設定」。ローカル：`.env`） |
| 鍵の長さ | 43文字（作り方：`python -c "from app.crypto import generate_key; print(generate_key())"`） |
| `SECRET_KEY` との関係 | **別の鍵**。`SECRET_KEY` は、ログイン状態の署名用（変えると、全員のログインが切れるだけ） |
| 暗号化の対象 | 緯度・経度のみ（備品の最後の位置、位置の記録）。誤差・高度・社員番号は、暗号化しない |

**鍵の取り扱い（重要）**
- **鍵を失うと、保存した座標は、二度と読めません。** 鍵は、パスワード管理ツールなど、**Azure以外の場所にも、必ず控えて**ください（リポジトリには、入れません）。
- **鍵を変えると（別の値にすると）、以前の座標は、読めなくなります。** 変更したい場合は、先に、旧い鍵で復号して、新しい鍵で、暗号化し直す作業が必要です（相談してください）。
- 鍵が設定されていない、または、形式が違うと、**アプリは起動しません**（誤って、暗号化なしで動かないようにするためです）。
- Web App の管理者（アプリ設定を読める人）は、鍵を見られます。厳密に分けたい場合は、Azure Key Vault に鍵を置く構成を、検討します。

**既存のDBの座標を、暗号化するとき（一度だけ）**
1. バックアップを取り、鍵を用意する（Azureのアプリ設定にも、同じ鍵を登録する）。
2. 確認だけ：`python tools\encrypt_coordinates.py`（DBの接続情報と鍵を、環境変数に入れて実行。何も変更しない）
3. 実行：`python tools\encrypt_coordinates.py --apply`（テーブルごとに、元の値と一致することを確認して、列を置き換える。失敗したら、元に戻る）
4. **直後に、新しいコードをデプロイする**（古いコードは、暗号化された列を読めないため）。

## 7. バックアップ・ログ・費用
- **DB**：Azure SQL の標準のバックアップ（自動）。復元は、ポータルの SQL データベース →「復元」から、新しいDBとして行います。
- **ログ**：`az webapp log tail -g rg-tanaoroshi -n rs-mobi-tana`、またはポータルの「ログストリーム」。
- **費用**：月額約$19（約2,900円、税別）。App Service B1 が約$14、SQL Basic が約$5.5です。停止しても課金は続きます。PoC終了後は、リソース グループごと削除すると、課金が止まります（**削除前に、必要なデータをCSVで出力してください**）。
